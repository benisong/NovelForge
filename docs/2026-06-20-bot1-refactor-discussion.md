# 2026-06-20 Bot1 架构重构讨论纪要

## 当前共识

### 1. 现有 Bot1 的结构性问题
当前 Bot1 在一次回复里同时承担三类任务：

- 与用户聊天
- 更新总大纲 / 当前大纲
- 输出标准格式化结果

这会显著分散模型注意力，导致：

- 聊天质量与规划质量互相拖累
- 为满足格式而牺牲规划深度
- 大纲更新不稳定、容易遗漏

结论：**Bot1 需要后端拆解职责，降低单次调用的认知负载。**

---

### 2. 拆解方向：聊天链路与大纲链路分离
当前讨论形成的方向是：

- **聊天链路**：继续负责与用户自然对话
- **大纲链路**：独立负责大纲维护 / 更新

重点不是前端拆分，而是**后端拆解工作职责**，让 AI 一次只处理一类问题。

---

### 3. 引入调度器
计划引入一个调度器，负责判断：

- 当前这轮或这一段聊天，是否需要触发大纲更新
- 如果需要，应当提取哪些上下文送去大纲维护模型

调度器不负责生成大纲本身，而是负责：

- 判断时机
- 截取上下文
- 派发更新任务

---

### 4. 用户输入达到阈值时的处理方式
已讨论出一个关键机制：

- 当聊天上下文达到阈值时，程序触发大纲更新
- 前端仍允许用户继续输入
- 但这些输入**先缓存，不立即发送给聊天模型**
- 等大纲更新完成后，再把：
  - 新大纲
  - 缓存的用户输入
  一起交给聊天模型

这样可以避免：

- 旧大纲覆盖新聊天
- 后台更新与前台聊天并行造成状态分叉
- 复杂的异步写回竞态

这个方案本质上是：

**阶段性冻结模型输入，但允许前端继续积累用户输入。**

---

### 5. Bot1 聊天模型的上下文拼接思路
对用户聊天的 `bot1`，当前讨论出的提示词顺序是：

1. 系统提示词
2. 大纲
3. 历史消息
4. 用户输入

目的：

- 让大纲位于更高注意力位置
- 历史消息放在后面，避免喧宾夺主
- 当前输入仍然作为最后落点

即：

**系统提示词 → 大纲 → 历史消息 → 用户输入**

---

### 6. 大纲维护模型职责调整
当前进一步讨论出的方向：

- 不让原 Bot1 同时维护总大纲和聊天
- 考虑引入专门的大纲维护链路

但随后又进一步细化：

#### 当前新共识
- **总大纲原则上不应由 Bot1_1 来维护**
- 总大纲更适合由 **Bot4 或 4_1** 维护，因为这更接近长期记忆 / 全局状态管理
- `Bot1_1` 更适合维护**当前章节规划 / 当前轮对话影响的近期规划**

也就是说：

- **Bot4 / 4_1**：长期、全局、低频更新
- **Bot1_1**：短期、局部、高频规划

---

### 7. 总大纲不能直接发给 Bot2
这是当前讨论中已经明确下来的硬规则：

**总大纲原则上不发给 Bot2 进行写作参考。**

原因：

- 会让 Bot2 获得超出当前章节应知范围的信息
- 容易引发剧透
- 会破坏悬念、伏笔和角色视角控制
- 会让 Bot2 带着“作者全知视角”写正文

结论：

- Bot2 不能直接读取总大纲
- Bot2 只能读取与当前章节相关、且不会泄露未来信息的局部上下文

这意味着后续可能需要单独定义一层：

- **Bot2 可见上下文 / 写作包**

它应当来自长期记忆与当前规划的筛选结果，而不是直接暴露总大纲。

---

### 8. 总大纲不能凭空产生，必须有显式生成流程
讨论中已明确：

- 总大纲不能靠 Bot4 自动“长出来”
- Bot4 / 4_1 更适合维护已有总纲，而不是在没有正式总纲时从聊天碎片中凭空生成
- 因此系统必须存在一个**显式的总纲生成流程**，用于形成初始正式总纲

也就是说，应当区分两阶段：

- **总纲生成**：第一次形成正式总纲
- **总纲维护**：在已有总纲的前提下进行更新和修正

---

### 9. 增加隐藏入口：总纲设计 / 总纲修正
当前讨论已经形成清晰方向：

- 在设置界面增加一个**隐藏按钮 / 隐藏入口**
- 当项目没有总纲时，可以进入**总纲设计模式**
- 当项目已有总纲但用户不满意时，可以进入**总纲修正模式**

该入口不作为日常主界面的高频入口，而是作为更高层级的创作控制入口。

---

### 10. 总纲设计 / 修正也采用 bot1 + 1_1 双链模式
总纲工作流内部仍然采用类似 Bot1 的双链路：

- **bot1**：与用户聊天、讨论方向、澄清意图
- **bot1_1**：负责输出和维护标准化总纲草稿

但这个流程不再服务于章节规划，而是专门服务于**总纲设计 / 总纲修正**。

---

### 11. 总纲设计与总纲修正共用同一套草稿机制
已达成共识：

- 总纲设计与总纲修正可以共用同一套草稿保存机制
- 区别只在于草稿初始化来源：
  - **总纲设计**：草稿初始为空
  - **总纲修正**：草稿初始拷贝自正式总纲

这样能够统一后端状态管理，并减少重复逻辑。

---

### 12. 总纲修正必须显式提交，不保存则舍弃
这条已经明确为硬规则：

- 总纲设计 / 修正过程中生成的是**草稿态总纲**
- 只有当用户点击**提交**时，草稿才会覆盖正式总纲
- 如果用户点击**不保存**，则本次修改直接舍弃
- 正式总纲保持不变
- 不能自动合并、不能后台偷偷保留未提交修改

这意味着总纲至少需要逻辑上区分：

- **正式总纲**
- **草稿总纲**

---

### 13. 总纲工作区需要一个类 Bot1 的独立界面
已达成共识：

- 总纲设计 / 修正不应直接塞进普通 Bot1 页面
- 需要一个**独立的总纲工作区**
- 该工作区可以复用 Bot1 的交互模式，但不能完整复制 Bot1 界面
- 因为总纲与章节大纲属于不同层级的对象，展示结构必须区分

当前最小化方向是：

- **聊天区**
- **总纲草稿展示区**
- **提交 / 放弃操作区**

---

### 14. 初始项目流程：无项目 → 创建项目 → 默认进入总纲设计界面
已形成明确主流程：

- 当用户当前没有项目时，系统应提示其先创建项目
- 创建项目成功后，默认进入**总纲设计界面**
- 在没有正式总纲前，不应直接进入普通章节级聊天 / 规划流程

这意味着项目生命周期至少包含以下阶段：

- **无项目**
- **有项目，无总纲**
- **总纲设计中**
- **有正式总纲**
- **总纲修正中**

同时，项目创建阶段建议最小化，只要求用户填写：

- **项目名**

其余信息在总纲设计过程中逐步补齐。

---

## 当前尚未定死、后续继续讨论的点

### A. 调度器的触发规则
虽然已经提出“聊天上下文达到阈值时触发”，但仍未完全定死：

- 是按字数阈值触发
- 按对话轮数触发
- 还是混合阈值触发

### B. Bot1_1 的输入切片规则
尚未完全确定：

- 阈值触发时截取哪一段消息
- 包含哪些 assistant 消息
- 包含哪些 user 消息
- 是否附带当前章节规划 / 近期摘要

### C. Bot4 / 4_1 维护总大纲的具体触发时机
已形成倾向，但还未最终定案：

- 不宜像聊天阈值一样高频触发
- 更可能适合在“阶段确认后”更新

### D. Bot2 的可见信息边界
已形成原则，但还未整理成正式规则表：

- 哪些信息允许给 Bot2
- 哪些信息绝对不能给 Bot2

### E. 总纲工作区的正式状态字段设计
当前已收敛出一版 **P0 最小状态字段集合**：

- `current_outline`
  - 继续复用，语义收紧为：**正式总纲**
- `outline_draft`
  - 总纲设计 / 修正过程中的草稿总纲
- `outline_mode`
  - 当前是否处于总纲工作流
  - 建议值：`"" | "design" | "revise"`
- `outline_dirty`
  - 当前草稿是否存在未提交修改

#### 当前 P0 状态流转规则

**1. 创建项目后默认进入总纲设计**

```json
{
  "current_outline": "",
  "outline_draft": "",
  "outline_mode": "design",
  "outline_dirty": false
}
```

**2. 进入总纲设计时**

- 初次进入：草稿为空，`outline_mode = "design"`
- 一旦 bot1 / bot1_1 在总纲设计工作区生成了草稿内容：
  - 只更新 `outline_draft`
  - 将 `outline_dirty` 置为 `true`
  - 绝不改动 `current_outline`

**3. 进入总纲修正时**

先从正式总纲复制一份草稿：

```json
{
  "current_outline": "正式总纲",
  "outline_draft": "正式总纲",
  "outline_mode": "revise",
  "outline_dirty": false
}
```

之后所有修改只落到 `outline_draft`，一旦发生变更，`outline_dirty = true`。

**4. 总纲设计 / 修正过程中的 AI 输出**

统一规则：

- bot1 / bot1_1 只更新 `outline_draft`
- 不允许直接更新 `current_outline`
- 正式总纲只能在用户点击“提交”时发生变化

**5. 用户点击“提交”时**

提交后草稿覆盖正式总纲，并退出总纲工作流：

```json
{
  "current_outline": "outline_draft 的内容",
  "outline_draft": "",
  "outline_mode": "",
  "outline_dirty": false
}
```

**6. 用户点击“不保存”时**

统一规则：

- 直接舍弃 `outline_draft`
- `current_outline` 保持原样（若原本为空则继续为空）
- `outline_mode` 退出
- `outline_dirty` 清零

即“不保存”= 本次总纲设计 / 修正会话作废。

**7. 用户切换界面时**

当且仅当：

- `outline_mode !== ""`
- 且 `outline_dirty === true`

才强提示用户：

- 提交
- 不保存
- 取消离开

**8. 项目重新加载时**

当前倾向：

- 允许草稿态持久化保存到项目中
- 如果项目加载时仍处于 `outline_mode = "design" / "revise"` 且 `outline_dirty = true`
- 则重新进入总纲工作区，并继续显示 `outline_draft`

但注意：

- 草稿持久化 ≠ 正式总纲生效
- 只有“提交”动作才能让 `outline_draft` 覆盖 `current_outline`

---

## 当前阶段性结论

本次讨论已经明确：

1. 现有 Bot1 一边聊天一边生成大纲，属于结构性注意力问题
2. 应通过后端拆解，分离聊天链与大纲链
3. 需要引入调度器负责判断与派发大纲更新
4. 大纲更新期间，前端可继续接收输入，但应先缓存，不立即送聊天模型
5. Bot1 聊天模型的提示词应调整为：系统提示词 → 大纲 → 历史消息 → 用户输入
6. 总大纲更适合交给 Bot4 / 4_1 维护，而不是 Bot1_1
7. 总大纲原则上不能直接发给 Bot2，以避免剧透与全知视角污染
8. 总大纲不能凭空生成，必须有显式的总纲设计流程
9. 系统需要在设置中提供隐藏的总纲设计 / 修正入口
10. 总纲设计 / 修正流程采用 bot1 + 1_1 双链模式，但服务对象是总纲而非章节大纲
11. 总纲设计与总纲修正共用同一套草稿机制
12. 用户点击“不保存”时，必须直接舍弃草稿修改
13. 前端需要一个类 Bot1 的总纲专用工作区，而不是直接复用普通 Bot1 页面
14. 无项目时应先创建项目，项目创建成功后默认进入总纲设计界面
